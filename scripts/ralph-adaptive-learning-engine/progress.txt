## Codebase Patterns
- Shared package is single file: `packages/shared/src/index.ts` (~1700 lines), all types/constants exported from there
- Shared must build first (`npm run build -w @ace-prep/shared`) before server/client typecheck
- ExamSize type is `10 | 15 | 25 | 50` from `EXAM_SIZE_OPTIONS` const array
- Use `as const` for constant arrays, derive types with `(typeof X)[number]`
- Pre-existing lint warnings (192) are all `no-console` and `no-explicit-any` — no errors
- lint-staged runs automatically on commit via pre-commit hook
- Migrations in `startupMigrations.ts` use synchronous better-sqlite3 only — no async/await
- Latest migration version is 13 — next should be 14
- Schema type exports go at the bottom of `schema.ts` with pattern `TypeRecord` (select) and `NewType` (insert)
- Drizzle schema table definitions use `sqliteTable` with index functions as 3rd arg returning array
- Tests mocking db: use `vi.hoisted()` to declare mock fns, then `vi.mock('../db/index.js', () => ...)` with those refs
- `feedbackService.test.ts` has pre-existing NODE_MODULE_VERSION failure — ignore in test runs
- Export `_testing` object from services for direct unit testing of pure functions (avoids heavy DB mocks)
- Don't use `require()` in tests for ESM modules — use static `import` after `vi.mock()`
- Only destructure mock refs you use in test assertions — lint catches unused destructured vars from hoisted blocks
- `selectQuestions()` returns `number[]` (IDs) — fetch full records via `inArray(questions.id, ids)` for response creation
- `recordEncounters()` is synchronous — no await needed, call after response insertion
- `updateQuestionStats()` and `recalibrateIfReady()` are synchronous — call fire-and-forget from answer submission paths

## 2026-02-12 - US-008
- Implemented: `difficultyCalibration.ts` with `updateQuestionStats(questionId, isCorrect)`, `recalibrateIfReady(questionId)`, `getCalibratedDifficulty(questionId)`
- `updateQuestionStats` increments attemptCount (always) and correctCount (if correct) on questions table using SQL increment expressions
- `recalibrateIfReady` checks min 5 attempts threshold, computes Bayesian confidence = 1 - 1/sqrt(sampleSize), derives empirical label (>80%=easy, 50-80%=medium, <50%=hard), blends with original via numeric mapping (easy=1, medium=2, hard=3) and stores result
- `getCalibratedDifficulty` returns empiricalDifficulty if set, falls back to original difficulty, defaults to 'medium' for missing questions
- Exports `_testing` object with pure functions: `empiricalLabel`, `confidence`, `blendDifficulty`, `difficultyToNumeric`, `numericToDifficulty`
- 24 unit tests covering: empirical label thresholds, confidence curve behavior, difficulty numeric mapping, blend formula at 0/0.5/1 confidence, updateQuestionStats correct/incorrect paths, recalibrateIfReady threshold/calibration behavior, getCalibratedDifficulty fallback chain
- Files changed: `packages/server/src/services/difficultyCalibration.ts`, `packages/server/src/services/difficultyCalibration.test.ts`
- **Learnings for future iterations:**
  - Bayesian confidence `1 - 1/sqrt(n)` is 0 at n=1, ~0.553 at n=5 (threshold), approaches 1 — good gradual ramp
  - Numeric difficulty mapping (easy=1, medium=2, hard=3) allows linear interpolation then re-bucketing via thresholds (≤1.5=easy, ≤2.5=medium, >2.5=hard)
  - `updateQuestionStats` and `recalibrateIfReady` are both synchronous (no async) since they use `.run()` — can be called fire-and-forget from answer submission paths
  - Keep `getCalibratedDifficulty` async for consistency with other read services, even though better-sqlite3 is synchronous under the hood
